# Adopting Flyway

Status: **done.** `spring.jpa.hibernate.ddl-auto=validate` — meaning entity
mappings not matching the schema fail startup — plus a full `./mvnw verify`
(478 tests) both pass against the Flyway-built schema.

## Why

Migrations were 110 hand-written `.sql` files applied by running `psql -f`.
Nothing recorded which ones went into which database. The only thing standing
between that and silent drift was `ddl-auto=validate`, which refuses to start
the application when an entity maps to a column that is not there.

That guard is real but narrow. It catches a missing column behind a mapped
field. It does not catch a missing index, a missing check constraint, a
missing trigger, or a data-transform migration that was never run — none of
which Hibernate validates, and all of which change behaviour.

## Why Flyway and not Liquibase

Liquibase wants a changelog in XML/YAML/JSON. Applying it here would have
meant either rewriting 110 SQL scripts into changesets or wrapping each in a
`<sqlFile>` include. The first is a large, error-prone rewrite of scripts
that were already correct; the second is an index over the files that adds a
format without adding information.

The abstraction would also not have survived contact with these particular
scripts. They use dollar-quoted `DO $$ ... $$` blocks, `pg_constraint`
lookups, trigger registration and audit-table wiring — PostgreSQL-specific
work that Liquibase's database-agnostic changeset types cannot express, so it
would have ended up as raw SQL inside a changeset wrapper anyway. The
portability that justifies Liquibase was not being bought.

Flyway reads plain `.sql` files in version order, which is what the
repository already had. The change was mostly a rename.

## What changed

- **`src/main/resources/db/migration/V1__baseline.sql`** is now the only
  thing Flyway applies. It is the schema and reference data that the old 110
  scripts produce when run in order, generated by actually building a
  database that way and dumping it — not written by hand. Its own header
  documents the exact recipe.
- **The 110 old scripts moved to `src/main/resources/sql/archive/`**, plus a
  README explaining why they are kept (most document a real decision, not
  just SQL) and that nothing runs them automatically anymore.
- **`src/test/resources/db/baseline-schema.sql` and `reference-data.sql`
  moved to `src/test/resources/db/archive/`** — they built the pre-Flyway
  test schema; `AbstractIntegrationTest` no longer needs them.
- **`AbstractIntegrationTest`** dropped the ~70-line hand-rolled schema
  builder (`loadSchema()`, `migrationScripts()`, `BASELINE_CUTOFF`). Spring
  Boot's Flyway auto-configuration now migrates the Testcontainers database
  automatically at context startup, using the same `db/migration` scripts a
  real deployment uses. Tests and the running application build their schema
  through the same mechanism for the first time.
- **`pom.xml`** gained `spring-boot-starter-flyway` and
  `flyway-database-postgresql`.
- **`application.properties`** documents the new mechanism in place of the
  old "this project has no Flyway" comment; `ddl-auto=validate` stays, as a
  second, independent, free check.

## Why this was simpler than the plan below originally assumed

The plan as first written assumed a live production database that `master`
needed to be reconciled against first, with `schema-diff.sh` proving an empty
diff before any baseline could be trusted — otherwise a baseline could assert
"this database already has everything" about a database that did not, and
Flyway would silently never run the missing piece.

That precondition turned out not to apply: nothing had been deployed yet, so
there was no live schema to match and no risk of asserting something false
about one. `V1__baseline.sql` was generated straight from a freshly built
reference database — see the file's own header for the exact steps, which
match the ones `schema-diff.sh` still uses to build its comparison side.

`schema-diff.sh` and `schema-inventory.sql` are kept — the question they
answer ("does this real database already match what the repository's
migrations describe?") is exactly the one to ask again before any future
re-baseline, or before pointing Flyway at a database this project did not
create from scratch.

## Two bugs `schema-diff.sh` caught before this shipped

Both were found by actually running the script against real disposable
databases, not by review:

1. **`schema-inventory.sql` failed with `operator is not unique: unknown ||
   "char"`.** `pg_attribute.attidentity`, `pg_attribute.attgenerated` and
   `pg_constraint.contype` are PostgreSQL's `"char"` catalog type, not text —
   concatenating one with `||` is ambiguous between competing operator
   overloads. Fixed with explicit `::text` casts.
2. **The failure-path output could exit `141` (SIGPIPE) instead of the
   intended `1`.** `grep | head -40 | sed` let `head` close the pipe as soon
   as it had its 40 lines, which under `set -o pipefail` could kill `grep`
   and end the script before it reached its own `exit 1`. Fixed by having
   `grep` write to a file first, so `head` reads from something that is not
   a live process on the other end of a pipe.

Also worth recording: **`pg_dump`'s default format uses `COPY ... FROM
stdin`**, a psql/libpq wire-protocol feature that a JDBC `Statement` — which
is how Flyway executes scripts — cannot run. `V1__baseline.sql` was dumped
with `--inserts` specifically so it is plain, standalone SQL.

## A Spring Boot 4 gotcha worth remembering

`flyway-core` on the classpath is not enough to activate Flyway under Spring
Boot 4. Boot 4 split `FlywayAutoConfiguration` out of the core autoconfigure
jar into its own module (`spring-boot-flyway`), pulled in by the
`spring-boot-starter-flyway` starter — the same pattern this project already
had for `spring-boot-starter-webmvc`. Without the starter, Flyway's
autoconfiguration class is simply absent from the classpath, so
`@ConditionalOnClass` never has anything to activate: no error, no log line,
just Hibernate reaching an empty schema and failing with "missing table."
That silence is what makes it worth writing down.

## Known constraints, still true

- **`PayrollValueBackfillIT` replays one archived script by filename**
  (`2026-08-01-03-employee-payroll-value-backfill.sql`, five call sites via
  `AbstractIntegrationTest.runMigrationScript`). It tests a data transform by
  feeding it known rows and reading back what it produced — the migration's
  own `DO $$` verification block only checks whatever it finds in the
  database it runs against, which on a Flyway-built schema is nothing it was
  meant to transform. If that file moves again, update both the path in
  `AbstractIntegrationTest` and the `SCRIPT` constant in the test.
- **The 37 pre-`2026-07-21` scripts were never independently re-verified by
  this change.** They were checked against a clone of the dev database by
  hand, back when they were written, and their combined effect is now folded
  into `V1__baseline.sql` — building the reference database that produced V1
  did apply them, successfully, as part of that one-time process.
- **New migrations go in `db/migration` as `V<version>__<description>.sql`**,
  not in `sql/archive`. The archive is history, not an active path.
